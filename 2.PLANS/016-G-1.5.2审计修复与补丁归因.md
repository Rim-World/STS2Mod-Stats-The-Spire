## 1. 目标

在单人本地统计 Mod 的范围内，完成一次可发布的 1.5.2 维护版本。范围只有四类：

1. 修正玩家可见的覆盖层残留与回放状态污染。
2. 修正已经确认的统计错误，重点是生成卡重复计数、Boss 白兽雕像药水、PaleBlueDot 贡献归因。
3. 降低写盘频率，增加原子写，避免半截 JSON 覆盖旧数据。
4. 删除确认无消费者的补丁，保留真正的跨版本兼容补丁；不扩大补丁面。

本计划不追求“修完 018 报告全部条目”。018 报告是审阅清单，不是施工单。

## 2. 范围

- 游戏版本：只保证 `v0.111.1` 与 `v0.113.1`。
- 玩家模型：单人本地；不承诺完整多人队伍统计。
- 游戏档案：只有一个游戏 profile；不做 profile 分区迁移。
- 第四幕：不实现；当前没有第四幕。
- 更旧游戏版本：不兼容；不需要为了旧版本保留死补丁。
- 发布形态：一个 `sts2_statsthespire_local.dll`，硬依赖 RitsuLib。
- 数据目录：沿用 `%AppData%/sts2_community_stats`。
- UI：只修四个已知覆盖层与两个已知状态污染点。

## 3. 非目标

以下项目明确不做，避免把维护版本变成重写：

- 不做完整多人聚合。保留 SP-048 的角色筛选本地玩家语义，不扩展卡牌、遗物、路径、先古、Boss、商店、回合计数的多人队伍统计。
- 不做 Profile 数据分区。用户只有一个游戏 profile，现有缓存混合风险不在本版本处理。
- 不做完整 UI 生命周期矩阵与 CI 门禁。只做四个覆盖层的定向 E2E。
- 不做缓存 LRU、TTL、取消框架。只做 debounce、最后一次请求生效和简单 generation 检查。
- 不重构 `CreateClassProcessor` 类级补丁注册。
- 不删除 `FiddleDrawCompatPatch`、`VoidFormEnergyCostPatch`。
- 不增加 `Kill` 重载、`OrbChanneled` 参数补丁。没有双版本目标确认前，不扩大补丁面。
- 不修改先古“选率/份额”的显示口径。
- 不修成就页重叠、`DuplicateFlags.Signals`、`QueueFree` 同帧顺序。
- 不重写 Git 历史。日志隐私处理是否重写历史，单独请求批准。
- 不重新引入 Baselib，不替换 RitsuLib。

### 4.1 PaleBlueDot 的真实调用链

`PaleBlueDot` 是储君（Regent）的卡牌「暗淡蓝点」。它不是无意义补丁。

游戏侧调用链：

1. `PaleBlueDot.OnPlay` 施加 `PaleBlueDotPower`：`STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models.Cards/PaleBlueDot.cs:24-28`。
2. `PaleBlueDotPower.AfterCardPlayed` 在本回合第 5 次出牌后，延迟 0.5 秒，施加 `DrawCardsNextTurnPower`：`.../PaleBlueDotPower.cs:42-56`。
3. `DrawCardsNextTurnPower.ModifyHandDraw` 在下回合抽牌时增加 `Amount`：`.../DrawCardsNextTurnPower.cs:18-29`。
4. Mod 已经补了 `DrawCardsNextTurnPower.ModifyHandDraw`，会把额外抽牌记入贡献：`9.SRC/src/Patches/CombatHistoryPatch.cs:2600-2614`。

真正的问题：

- `PaleBlueDotPower` 没有 `ModifyHandDraw`，所以旧补丁目标不存在。
- 第 5 次出牌时，`PaleBlueDotPower` 是在异步延迟后施加 `DrawCardsNextTurnPower`。来源有两种未验证结果：第 5 张攻击牌仍作为当前卡牌，或当前上下文已清空。两种情况都不能正确归到「暗淡蓝点」。
- `DrawCardsNextTurnPower` 的额外抽牌本身已经由现有补丁记录；缺的是这个 `DrawCardsNextTurnPower` 实例的来源映射。
- 如果直接给 `PaleBlueDotPower` 加普通主动上下文，Harmony 对 async 方法的 postfix 可能在第一次 `await` 后清掉上下文；不能只依赖 `PowerHookContextPatcher` 的现成模式。

因此，修复目标不是“再加一个 ModifyHandDraw 补丁”，而是：

1. 在 `PaleBlueDotPower.AfterCardPlayed` 触发第 5 次效果时，捕获「暗淡蓝点」这个来源。
2. 在随后施加 `DrawCardsNextTurnPower` 时，把来源写到该 Power 的映射。
3. 让现有 `DrawCardsNextTurnPower.ModifyHandDraw` 补丁读取正确来源。
4. 确保额外抽牌只记一次，不重复。

### 4.2 四个记录补丁为什么“完全无用”

`RunDataCollector` 的四个方法明确是空实现：

- `RecordCardReward`：`9.SRC/src/Collection/RunDataCollector.cs:68`。
- `RecordEventChoice`：`:69`。
- `RecordCardRemoval`：`:70`。
- `RecordCardUpgrade`：`:71`。

当前本地版的路径统计来自 `RunHistory.MapPointHistory` 的 `CardsRemoved`、`UpgradedCards`、`CardsGained`、`BoughtColorless`：`RunHistoryAnalyzer.cs:510-575`。

因此：

- 这四组补丁的钩子本身可能正确。
- 但下游没有消费者，录了也不进入任何统计。
- 重新实现它们会与 RunHistory 统计重复计数。
- 正确动作是删除补丁，或不改代码并标记为保留 ABI。

### 4.3 Fiddle 与 VoidForm 不是死补丁

- `Fiddle` 两版都重写 `ModifyHandDraw`：`STS2-Reference/2.STS2-111Reference/.../Fiddle.cs:15-22`；`4.STS2-113.1Reference/.../Fiddle.cs:15-22`。
- `VoidFormPower` 两版都重写 `TryModifyEnergyCostInCombatLate`：`.../VoidFormPower.cs:81-89`。
- 当前补丁目标正确，不能因为“看起来没有效果”就删除。

## 8. 风险与回退

| 风险 | 处理 |
|---|---|
| PaleBlueDot 的 async 来源捕获不稳定 | 先做探针原型；无法可靠清除 stale 来源时，接受“未归因”，不记到错误卡牌 |
| 删除四个记录补丁影响路径统计 | 用固定 RunHistory 夹具比较前后；路径统计来自 MapPointHistory，不来自这些补丁 |
| 写盘节流导致退出丢数据 | 战斗结束、跑局结束、退出前强制 flush；测试强制退出 |
| 原子写在目标文件不存在时失败 | 首次写用临时文件 + 移动；替换失败回退普通写并记录警告 |
| 1.5.2 版本号遗漏 | 版本验证脚本检查 manifest、代码、csproj、README、CHANGELOG、输出目录 |
| 测试污染真实存档 | 使用独立 profile/临时目录；测试结束清理部署与进程 |
| 删除自动清理改变用户预期 | 在 README/CHANGELOG 明确说明不再自动删除历史贡献数据 |
