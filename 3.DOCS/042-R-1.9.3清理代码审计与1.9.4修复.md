## 2. 确认缺陷

### P1 当前存档保护路径失效

1.9.3 把 `SaveManager.Instance.GetProfileScopedPath("saves")` 直接交给 `System.IO.File.Exists`。

游戏源码链路：

- `SaveManager.GetProfileScopedPath` 调用 `_saveStore.GetFullPath(...)`。
- `GodotFileIo.GetFullPath` 返回 `SaveDir + "/" + filename`。
- `SaveDir` 来自 `UserDataPathProvider.GetAccountScopedBasePath(null)`，是 `user://...`。
- 游戏自己的 `OpenConsoleCmd` 也必须再调用 `ProjectSettings.GlobalizePath`。

因此 1.9.3 的 `File.Exists` 恒为 false，`hasSave=false`、`parseFailed=false`，清理以空保护集继续。

实测：

```text
path raw=user://steam/76561198869461680/modded/profile1\saves
resolved=C:/Users/13167/AppData/Roaming/SlayTheSpire2/steam/76561198869461680/modded/profile1\saves
exists=True ok=True
```

### P2 只保护当前 profile

游戏有 3 个 profile；贡献数据在账号级共享。1.9.3 只读取 `SaveManager.CurrentProfileId`。其他 profile 的暂停局对应目录超过 90 天时仍会被删除。

### P3 删除任意旧目录

1.9.3 对 `contributions/` 下所有顶层目录按 mtime 删除，不校验 `{StartTime}_{seed}`。用户手工放入的旧备份目录会被整目录删除。

### P4 嵌套 reparse 仅顶层检查

1.9.3 只检查顶层 run 目录是否为 reparse point。嵌套 junction/symlink 不会删除外部 target 内容，但可能造成部分删除或异常。修复采用全树预扫描并跳过整个 Run 目录。

### P5 探针放过 P1

1.9.3 探针只打印 `HasCurrentSave`，未纳入 PASS；日志已显示 `hasSave=False`，最终仍 `RESULT PASS`。探针只使用临时目录和合成 JSON，未走真实 `GetProfileScopedPath`。

## 3. 1.9.4 修复

- `ResolveFileSystemPath`：将 `user://`/`res://` 转为 OS 路径；空路径视为解析失败并跳过清理。
- `ReadCurrentRunRefs`：读取 `ProfileSaveManager.maxProfileCount` 个 profile，合并所有当前 save 与备份的 StartTime/seed；任一 profile 路径无法解析或任一存档损坏则跳过清理。
- `Prune`：目录名必须由 `TryParseRunStart` 解析为 `{正 long}_{seed}`；未知目录保留。
- `ContainsReparsePoint`：根目录与所有后代预扫描；命中则跳过整个 Run 目录。
- `Prune`：`contributions/` 根目录本身是 reparse point 时也跳过。
- `ReadCurrentRunRefs`：saves 路径必须解析为绝对 OS 路径；否则跳过清理。
- `ReadCurrentRunRefs(IEnumerable<string>)`：规范化并校验每个目录；供探针验证多目录合并。
- 探针：
  - 真实 `GetProfileScopedPath("saves")` 转换断言。
  - 三个 profile 的 saves 路径断言。
  - 多 saves 目录合并断言。
  - 仅当真实 `current_run.save`、`.backup`、`current_run_mp.save`、`.backup` 全部不存在时，创建真实 `current_run.save`，断言 `HasCurrentSave=true`、StartTime/seed 命中、对应旧临时目录保留；`finally` 删除。
  - 未知旧目录保留断言。

## 5. 未验证与剩余风险

- 真实多 profile 暂停局未构造；只用合成 saves 目录验证合并逻辑。
- 真实存档与清理的竞态未做压力测试。
- `.backup` 主文件损坏、备份有效路径未单独运行。
- v0.111.1 的最终 1.9.4 运行探针待做。
- 用户视觉检查 RitsuLib 开关仍未做。
- 嵌套 junction/symlink 与根 `contributions` reparse 的跳过逻辑只做代码审阅，未在测试中创建 junction。
- `auto_cleanup` 值类型错误时，`GetBoolean` 抛出后外层 catch 保留默认 `true`；安全但可能不符合用户意图。
- 顶层任意旧 `*.json` 仍会被清理；当前范围只过滤目录。若用户在 `contributions/` 手工放 JSON 备份，仍可能被删除。
- 父目录 `%AppData%/sts2_community_stats` 若是 junction/symlink，根守卫只覆盖 `contributions` 本身，未覆盖父级。
- `File.Exists` 对 access denied 也返回 false，无法区分“不存在”与“不可访问”；当前只能依赖目录存在与路径可解析。
- 有效 `start_time` 但缺少 `rng.seed` 的当前存档只保护 Run 目录，legacy 文件按 seed 保护会遗漏。
- 预扫描与 `Directory.Delete` 之间仍有 TOCTOU；.NET 不跟随 reparse point，最坏后果是部分删除或异常。
- 目录 mtime 是目录条目时间，不是 Run 开始时间；久置续局依赖当前存档保护。
- 清理与 `RunHistoryAnalyzer` prewarm/`LoadAllAsync` 并发；删除中的目录可能产生 warning/半缓存，不崩。
- 真实 save 探针只在目标 profile 没有 current save 时运行；若已有暂停局则跳过 realPath 且仍 PASS。
