## 3. 为什么此前的审阅没有发现地图悬停残留

这不是单点疏忽，而是审阅范围与方法共同造成的盲区。

### 3.1 前几轮审阅的实际范围

- `3.DOCS/016-R-游戏规则官中术语与玩家可见性.md:399` 明确写「UI 布局、字体、动画不属于本轮范围」。该轮审的是规则数值、术语与玩家可见性，不是 UI 生命周期。
- `3.DOCS/012-R-1.5.0文档与代码一致性审阅.md` 审的是文档与代码一致性，不是运行时节点树。
- `3.DOCS/015-R-游戏公式与硬编码逻辑核对.md` 审的是公式与硬编码，不是界面状态机。
- `3.DOCS/017-R-RQ014修复与验证.md` 的独立审阅只覆盖 RQ-014 修复项，不能代表全场 UI 审阅。

### 3.2 静态审阅为什么会误判

`MapPointPatch` 在修复前已经有 `OnUnfocus` 删除面板的代码。静态阅读时，这段代码看起来是完整的：

- 地图点获得焦点 → 创建面板；
- 地图点失去焦点 → 删除面板；
- 面板挂在 `NMapPoint` 下。

审阅者默认了一个未经验证的 Godot 生命周期前提：**只要地图点失去焦点，面板就一定被删除；只要地图关闭，所有地图点就一定失焦**。

游戏侧的实际行为更细：

- `NMapScreen.Close(false)` 只设置 `Visible=false` 和 `ProcessMode=Disabled`，不遍历、不释放子节点。
- 关闭动画路径 `Close(true)` 会立即发出 `Closed`，但 `Visible=false` 要等 tween 完成。
- 隐藏屏幕会传播 `visibility_changed`；`NClickableControl.OnVisibilityChanged` 只会对**当前 `IsFocused` 为 true** 的控件清除焦点并调用 `OnUnfocus`。
- `Open` 复用已有地图点和子节点；`SetMap` 才会 `FreeChildren`。
- 因此，面板如果由某个**已经不在焦点**的点持有，或者创建路径没有走到正常焦点清理，就会在 `Close` 后保留；关闭动画期间也可能继续可见。

所以真正的缺陷是：**清理只挂在 `OnUnfocus` 一个事件上，覆盖面不足**。静态审阅没有继续追问“谁保证每个面板都有焦点、关闭动画和重开时的清理”，只看到 `OnUnfocus` 就认为闭环。

修复后的代码改为在 `Close`、`CleanUp`、`Open`、`SetMap` 主动清理，并登记所有面板；这是更稳妥的所有权模型。

### 3.3 测试为什么没有覆盖

- AutoSlayer 会走场景树和战斗流程，但不会模拟鼠标悬停、失焦、关闭地图、重开地图。
- 既有探针主要验证数值、设置页、对局身份与收尾，没有“UI 生命周期矩阵”。
- `MapFixProbe` 是用户反馈之后补的；它手动创建面板并手动登记到私有表，再调用 `screen.Close(false)`。它验证了修复后的清理，不是修复前的真实悬停路径；也没有覆盖 `Open`、`CleanUp`、`SetMap`、重开和视觉残留。
- 审查代理没有运行游戏，也没有截图或节点树快照；它们只能读代码。

### 3.4 流程上应该怎样补

1. 任何注入到游戏节点的 UI，都必须在设计文档中列出「创建、父节点、显示、焦点、关闭、清理、重开、换场景」八列生命周期矩阵。
2. 每个矩阵项至少有一个自动化断言：节点是否仍存在、是否仍可见、父节点是否正确、元数据是否已清除。
3. 不能把 `OnUnfocus`、`Close`、`Hide` 这类名字当作行为保证；必须读取游戏反编译实现或做运行时探针。
4. UI 审阅不能只做静态审阅；至少需要一次真实窗口的悬停、关闭、重开与截图。
5. 审阅报告必须写清“未覆盖的 UI 生命周期”，不能把静态源码审阅称为“全面”。

**证据**

### 4.3 P1-1：跑局历史弹窗在退出界面后仍残留

**证据**

- `9.SRC/src/Patches/RunHistoryPatch.cs:296` 将 `overlay` 直接加到 scene root。
- `CloseOpenPopup` 的调用点只有：
  - `AfterSelectPlayer`（进入/切换玩家）；
  - `OpenPopup` 自身开头；
  - 关闭按钮、遮挡层点击、Esc；
  - `RunHistoryStatsSection` 打开贡献面板前。
- 没有 `OnSubmenuHidden`、`_ExitTree` 或 `TreeExiting` 清理。
- 弹窗的 Esc 处理挂在 `overlay.GuiInput`，但 `overlay` 从未 `GrabFocus()`，子控件也没有获得焦点；键盘事件不会路由到它，Esc 分支实际上是死代码。游戏底层返回键会退出跑局历史，弹窗却留在主菜单。
- 游戏侧 `NRunHistory.OnSubmenuHidden`（`4.STS2-113.1Reference/.../NRunHistory.cs:403-408`）只禁用前后按钮并停止 tween，不处理根节点覆盖层。
- `overlay.MouseFilter = Stop`，覆盖全屏；`dim` 也是全屏 `Stop`。

**事件序列**

1. 进入跑局历史。
2. 点击「查看贡献图表」，打开弹窗。
3. 按返回键/关闭跑局历史界面，但不点弹窗的关闭按钮。
4. `NRunHistory` 隐藏；root 上的 `ModRunHistoryStatsPopup` 仍存在且可见。
5. 主菜单或下一屏被 `MouseFilter.Stop` 的遮罩拦截，直到重新进入跑局历史触发 `SelectPlayer`。

**影响**

用户会认为游戏“卡住”或“点不动”。这是和地图悬停残留同一类问题。

**建议**

- 给 `NRunHistory.OnSubmenuHidden` 或 `NRunHistory` 的 `TreeExiting` 加 postfix，调用 `CloseOpenPopup`。
- 让 `CloseOpenPopup` 在 `OpenPopup` 之前、界面隐藏时都幂等。
- 增加自动化断言：界面隐藏后 root 下不存在 `ModRunHistoryStatsPopup`。

### 4.4 P1-2：生涯统计标签页切到「成就」后内容重叠（条件性）

**证据**

- `StatsScreenTabPatch` 只给 `OpenStatsMenu` 加了 postfix：`9.SRC/src/Patches/StatsScreenTabPatch.cs:46-55`。
- 生涯标签点击回调把 `_statsGrid` 隐藏、把 `StsCareerTabContent` 显示：`:169-179`。
- 游戏侧 `NStatsScreen.OpenAchievementsMenu`（`4.STS2-113.1Reference/.../NStatsScreen.cs:171-175`）只把 `_statsGrid` 设为不可见，没有隐藏 `StsCareerTabContent`。
- 没有 `OpenAchievementsMenu` 的 postfix，也没有把成就标签连接到生涯容器的隐藏逻辑。
- 但 `NStatsScreen._Ready` 当前把成就标签 `Disable()`：`NStatsScreen.cs:151`。因此当前版本用户可能无法点击成就标签，问题不一定可触发；一旦游戏重新启用成就页，该缺陷会立即暴露。

**事件序列**

1. 打开「百科大全 → 角色数据」。
2. 点新增的「生涯统计」标签，生涯内容显示。
3. 点「成就」标签（前提：该标签被启用）。
4. `_statsGrid` 被隐藏，`StsCareerTabContent` 仍然显示；两套内容重叠。

**影响**

条件性 UI 错误：当前版本若成就标签保持禁用，用户看不到；若游戏后续启用，或者有其它代码触发 `OpenAchievementsMenu`，就会重叠。属于“代码缺陷已确认，当前可达性未确认”。

## 5. 已确认正常或基本正常的部分

这些结论同样重要，避免下一位维护者重复排查。

- **双版本可编译**：v0.111.1 与 v0.113.1 均 0 错误；仅有 7 个可空警告。
- **依赖漏洞**：`dotnet list package --vulnerable` 未发现已知漏洞。
- **无网络代码**：`9.SRC/src` 没有 `HttpClient`、`WebRequest`、`Socket`、`Process.Start`、`Assembly.Load` 等；联网声明对本 Mod 代码成立。RitsuLib 自身的遥测、localhost 调试服务与 Steam 云镜像见 P1-6。
- **无路径穿越（当前代码）**：`RunStorage.Sanitize` 替换路径分隔符，所有使用点都有固定前缀；安全审阅逐一检查 `Path.Combine` 调用点，未发现可逃出 `%APPDATA%\sts2_community_stats` 的输入。`..`、保留名和大小写碰撞属于纵深防御风险，见 P3-8。
- **无 unsafe / 无原生互操作**：`AllowUnsafeBlocks` 虽为 true，但源码无 `unsafe`、`stackalloc`、`DllImport`、`Marshal`；可以移除该属性，见 P3-7。
- **无反序列化 RCE**：全部使用 `System.Text.Json` 默认选项与具体 DTO，无多态类型、无 `TypeNameHandling` 等价物、无自定义 converter gadget。
- **无每帧轮询**：没有 `_Process`、`_PhysicsProcess`、`_Draw`、每帧计时器；唯一计时器是意图面板的 120 ms 延迟隐藏。

## 6. 性能子代理补充

`PerfMaint` 的独立审阅结论与本报告一致，并补充了以下需要纳入修复清单的点。

### 6.1 `GetCached` 不把磁盘快照放回内存缓存

- `RunHistoryAnalyzer.cs:63-85` 的注释说会 promote，代码直接返回 `CareerStatsCache.Load`。
- 每次切换角色/模式/进阶/最近局数都会重新读盘、反序列化。
- 启动时 `CommunityStatsMod.cs:44` 读取后又丢弃，`:51` 仍会全量扫描。
- 修复：读到后加锁写入 `_cache`；启动加载用 `force: true`。

### 6.2 过滤条件缓存无上限，最近局数 spinner 可排队全量扫描

- `_cache` 以 `(character, minAsc, recent, mode)` 为键，无淘汰：`RunHistoryAnalyzer.cs:35`。
- `recentSpin` 最大 9999：`CareerStatsSection.cs:366-372`。
- 每次值变化都触发 `LoadAllAsync`，没有取消：`:625-637`。
- 结果：拖动 spinner 会排队几十次全量历史扫描；每次 `InvalidateAll` 后重复。

### 6.3 跑局详情重复组装战斗文件

- `RunHistoryStatsSection.BuildReplayButton` 为了判断按钮是否可用，先调用 `LoadRunSummary`：`:458-462`。
- 点击按钮时再调用一次：`:466-471`。
- `LoadRunSummary` 在没有 summary 时会组装所有 `combat_*.json`：`ContributionPersistence.cs:170-190`、`:250-275`。
- 一个 25–50 场战斗的跑局，会重复 25–50 次文件读取与 JSON 解析。

### 6.4 隐藏的生涯面板仍会重建

- `CareerStatsSection.OnCareerStatsLoaded` 不检查可见性，直接 `CallDeferred(Rebuild)`：`:94-112`。
- 卡牌/遗物库的 `force: true` 加载会触发该事件：`CardLibraryPatch.cs:139`、`RelicLibraryPatch.cs:150`。
- 玩家离开生涯页后，缓存场景仍持有订阅；后续加载会重建数百个节点。

注意：删除 `CardRewardScreenPatch` 时必须保留 `AfterOverlayOpened`（隐藏贡献面板）；`AfterSelectCard` 可以删除。

### 6.6 不建议为了“短”而重构的部分

- `RunHistoryAnalyzer` 的九类聚合是独立查询，文件大但逻辑不同；真正的问题是缓存策略，不是行数。
- `IntentStateMachinePanel` / `ArrowOverlay` 是专用图布局渲染器，按约 30 张参考截图实现；按需提取纯布局算法即可，不建议重写。
- `MonsterIntentMetadata` 的克隆与状态机快照逻辑是必要的；只需要复核 eager bake 的时机。

### 6.7 重复的复制与辅助逻辑

- `ShopPurchasePersistence` 与 `ShopOfferingPersistence` 结构几乎相同；可合并为泛型 `RunFileStore<T>`。
- `ContributionAccum` 的深拷贝在三处重复：`ContributionPersistence.Clone`、`RunContributionAggregator.Clone`、`AddCombat` 内的 18 字段手写拷贝。新增字段时容易漏掉，且 `AddCombat` 的漏字段会静默丢数据。
- `CareerStatsSection.SectionPanel` 与 `RunHistoryStatsSection.WrapInPanel` 的样式与调色板重复；可提取共享 `StatsSectionUi`。
- `ContributionPersistence` 的 `ToDto/FromDto` 是手写 18 字段映射，没有编译器校验；建议共享映射器。

### 6.8 意图元数据的 eager bake 可能制造首战卡顿

- `MonsterIntentMetadata.Get(id, liveMonster)` 在战斗内总是从 live monster 重建，eager bake 只在没有 live monster 的回退路径有用。
- `BakeAllMonsters` 对约 121 个怪物 × 2 个进阶层级执行 `ToMutable` + `SetUpForCombat`，并把结果保留整个会话。
- 如果 mod init 时 `ModelDb` 尚未初始化，`CombatLifecyclePatch.AfterSetUpCombat` 会在第一场战斗的 postfix 中重试完整 bake；这是最可能的首战卡顿点。
- `ForcedAscensionDeadly` 是全局静态，`AscensionForcePatch` 在 bake 窗口内改变 `RunManager.HasAscension` 的返回值；如果未来把 bake 移到后台线程，必须改成作用域参数，不能保留全局可变状态。

### 6.9 282 条遗物 + 85 条能力的手写补丁表

- `CombatHistoryPatch` 中的 `TryPatch` 列表是逐版本人工核对的 367 条记录；每次游戏版本升级都要重新核验。
- 每条缺失目标都会写警告；当前两个版本没有触发，但维护成本高。
- 可以改为 `(Type, hookName)[]` 声明式表，单循环注册并输出一份汇总；是否能进一步用一个 Hook 调度级补丁替代，需要先确认游戏 `Hook` 是否把实例传给回调，不能凭猜测改。

### 6.10 结构拆分建议

- `CombatHistoryPatch.cs` 3,465 行，内部 34 个类；按已有分区注释拆成 `Patches/Context`、`Combat`、`Cards`、`Orbs` 等文件，零行为变化，主要降低审阅成本。
- `CombatTracker.cs` 1,557 行、60+ 个公开 mutator；`ForceResetAllContext` 与 `OnCombatStart` 已经出现字段清单重复，拆成 `SourceResolver` / `CombatLedger` / `OstyLedger` / `DoomLedger` / `CombatSnapshot` 更合适。
- `IntentStateMachinePanel` 的图布局算法（深度分配、Tarjan SCC、BFS 排序）是纯函数，可提取 `IntentGraphLayout` 并单测；不必重写渲染。
- `RunHistoryAnalyzer` 1,202 行、`CareerStatsSection` 1,491 行、`IntentStateMachinePanel` 1,512 行，体量大但职责相对独立；先修缓存与 UI 状态，再考虑拆分，不要为了行数做大规模搬家。
