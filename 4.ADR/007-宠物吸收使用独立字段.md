# 宠物吸收使用独立字段

- 状态：已接受
- 日期：2026-11-22
- 项目版本：1.6.1（决策时）；目标版本 1.7.0
- 相关文件：`1.PRD/001-项目范围与验收.md`、`2.PLANS/024-M-宠物吸收统计与展示.md`、`9.SRC/src/Collection/ContributionMap.cs`、`9.SRC/src/Collection/CombatTracker.cs`、`9.SRC/src/Util/ContributionPersistence.cs`、`9.SRC/src/UI/ContributionChart.cs`

## 背景

当前奥斯提用生命值替玩家承伤时，吸收量写入 `ContributionAccum.EffectiveBlock`。该字段的现有定义是“被格挡吸收的伤害”。瓦皮也有独立生命值，但当前只把敌方对瓦皮的伤害从玩家输出中排除，没有防御记录。

两者都适合放在同一个防御界面。玩家看到宠物行时，能够理解它们没有格挡，而是用生命值承伤。展示层不需要拆成两个面板。

问题在数据层：`EffectiveBlock` 同时保存“格挡消耗”和“宠物生命值消耗”后，无法回答以下问题：

- 本场战斗的格挡吸收是多少。
- 宠物生命值吸收是多少。
- 旧数据中的奥斯提数值应如何迁移。
- JSON、运行中快照和对局汇总是否使用同一口径。

如果继续复用 `EffectiveBlock`，所有下游消费者都会继承这个混合语义。

## 决策

新增独立字段 `PetAbsorbed`，专门记录宠物生命值实际吸收的伤害。`EffectiveBlock` 继续只记录格挡消耗。两者都进入防御总量和防御百分比，但存储、迁移和测试分开。

## 备选方案

### 复用 `EffectiveBlock`

优点是改动最小，不需要修改持久化结构，旧数据可直接继续读取。

缺点是无法区分格挡和宠物生命值；帮助文案会继续把宠物吸收描述成格挡；未来导出或拆分统计时仍要改字段。否决。

### 新增独立一级“宠物”分区

优点是完全不碰现有防御区。

缺点是同一类“伤害被挡住”的数值被拆到两个界面；用户已经明确希望在同一界面和标准展示；还会产生重复总量和重复百分比。否决。

### 只改 UI 文案，不改字段

优点是不改数据结构。

缺点是数据仍无法区分两类资源；对局汇总和 JSON 仍然混合；后续无法做精确迁移。否决。

## 后果

获益：

- 格挡与宠物生命值吸收可以分别核对。
- 奥斯提和瓦皮能在同一防御区显示，同时保留各自来源。
- 旧奥斯提数据可以显式迁移，不依赖字段含义的默认解释。
- 后续新增宠物时，可以复用 `PetAbsorbed` 和本地宠物过滤。

代价与约束：

- `ContributionAccum`、DTO、JSON、运行中快照、汇总和 UI 全部要同步。
- 旧数据需要迁移；迁移必须幂等，且不得双计。
- v0.111.1 没有瓦皮类型，瓦皮识别必须使用运行时类型名或安全反射，不能直接引用 v0.113 类型。
- 奥斯提死亡剩余 HP 的负防御语义需要单独固定，不得顺手改变。
- 版本号和输出包需要升级；目标版本为 1.7.0。

下游规则：

1. `EffectiveBlock` 不得再写入宠物 HP 吸收。
2. 宠物 HP 吸收只能写入 `PetAbsorbed`。
3. 防御总量必须同时包含 `EffectiveBlock` 和 `PetAbsorbed`。
4. 宠物承伤只统计实际失去的 HP，不计溢出伤害。
5. 宠物承伤只统计本地玩家的宠物。
6. 旧 `osty` 数据读取时必须迁移到 `PetAbsorbed`，迁移后清零旧字段的同一笔数值。
7. v0.111.1 路径不得直接引用 `Wuppy` 类型。
8. 展示层只保留一套宠物父行/子行，不新增重复分区。
9. 旧 `osty` 来源类型读取时必须归一化为 `pet`；`SourceId` 保留 `OSTY`，显示名仍为“奥斯提”。
10. `EffectiveBlock` 只表示实际挡住伤害的格挡。奥斯提剩余 HP 的机会成本不得写入 `EffectiveBlock`；若要保留，必须使用独立字段。
