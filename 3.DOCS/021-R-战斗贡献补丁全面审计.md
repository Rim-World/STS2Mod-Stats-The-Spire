## 0. 结论摘要

- 旧称“107 个补丁”实际是 107 个 `[HarmonyPatch]` 特性；当前有 361 条注册记录、343 个唯一 `Type.Method`（不含条件式 `OutbreakPower` 为 342）。
- 12 个切片已完成；目标名称和主要签名在 v0.113.1 与 v0.111.1 都能对上。
- 这不是“公式都写错了”的报告。多个核心机制是正确的；真正的问题是几条横跨全表的机制缺陷：
  - 真实伤害守卫挂错重载，v0.113.1 的多数减伤不入账。
  - 待定抽牌来源没有生命周期，下一次非手抽牌会被上一个 hook 抢走。
  - 格挡池在游戏没有真正清空格挡时被清空，锚/壁垒/残影/坚固钳子漏记。
  - 缩放仪、浴袍、皇家枕头、腰带扣等遗物的真实钩子没有上下文。
  - 失败战斗不 flush，最终战贡献丢失。
  - 生成卡来源、升级格挡、君王之剑锻造子条、费用节省和辉星存在重复或错源。
- 旧 issue 的三个点：缩放仪确认有同类根因；小血瓶与锁镰的旧症状在当前证据中未复现，但锁镰仍会被待定抽牌污染。
- v0.113 新增愚者、90 张职业卡、17 个遗物、3 个药水、5 个事件、41 个能力；通用命令覆盖大部分卡牌。完整统计预计新增约 50–70 个 hook 目标，不是按 121 个卡类逐张扩张。详见 §18。
- 本文是源码级审计；没有在 1.5.2 上做全量实机复现。旧运行证据只作旁证。

1. 玩家看到什么。
2. 游戏实际逻辑是什么。
3. 代码为什么会产生这个结果。
4. 当前版本能不能看到，以及建议。

| 状态 | 含义 |

| 确认 | 代码与游戏源码的调用链能直接对上 |

## 3. 核心伤害与击杀


### K1. 「瓦皮」替玩家承伤被记成对敌伤害

**现象**

持有「瓦皮」时，敌人攻击先由瓦皮承伤；这部分伤害被计入总伤害，常常落在「未归因」行，玩家防御却少记。

**游戏逻辑**

v0.113.1 新增 `Hook.ModifyPreBlockDamageTarget`，瓦皮把目标重定向到自己：

```text
../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models.Powers/WuppysLoyaltyPower.cs:28-43
```

**模组代码**

`AfterDamageReceived` 只区分 `receiver.IsPlayer` 与 `receiver.Monster is Osty`：`9.SRC/src/Patches/CombatHistoryPatch.cs:118-149`。瓦皮是玩家侧宠物，不是敌人，进入「对敌伤害」分支。

**判定**

确认（源码）。玩家在伤害图/DPS 可见。

**建议**

按 `receiver.Side` 和 `PetOwner` 判断敌人/玩家侧宠物；瓦皮的承伤应计入防御或明确不统计。

### K2. 奥斯提伤害不计入本场总伤害

奥斯提攻击卡造成伤害时，`OnDamageDealt` 在累加 `_totalDamageDealt` 之前从奥斯提分支返回；本场 DPS 因此偏低，而本局汇总按柱子求和又包含它。

**证据**

`9.SRC/src/Collection/CombatTracker.cs:576-581`；`:682-683`；`:1362-1383`。

**判定**

确认（源码）。建议统一口径：奥斯提伤害要么都计入总伤害，要么都排除。

### K3. 奥斯提补刀丢失奥斯提标记

`KillingBlowPatcher.CaptureKillingBlow` 调 `OnDamageDealt` 时没有传 `isOstyDealer`/`isOstyReceiver`，也没有 `IsInProgress` 守卫：`9.SRC/src/Patches/CombatHistoryPatch.cs:1980-1987`。奥斯提最后一击会从 OSTY 子条跳到普通卡牌直接伤害。

**判定**

确认（源码）。

### K4. 击杀补刀的修正来源属于最后一个目标

`IsEnding` 多目标批次中，`LastDamageModifiers` 在全部目标命中后只保留最后一个目标的修正；`KillingBlowPatcher` 逐结果补记时，第一个结果消费了最后一个目标的修正。总量通常不变，修正来源错。

**判定**

确认（源码）。建议按 `DamageResult` 缓存修正快照。

### K5. 玩家死亡标记误报与漏报

- 瓶中精灵/蜥蜴尾巴复活后，`DamageResult.WasTargetKilled` 仍为 true，`playerDied` 误报。
- 玩家被灾厄杀死走 `Kill → LoseHpInternal`，不经过 `DamageReceived`，`playerDied` 漏报。

**证据**

`9.SRC/src/Patches/CombatHistoryPatch.cs:151-152`；`CreatureCmd.cs:590-609`；`DoomPower.cs:40-55`。

**判定**

确认（源码）。当前 UI 未消费该字段，属于持久化正确性问题。

### K6. 总伤害包含被格挡部分

`TotalDamageDealt` 和 `DamageTakenByPlayer` 使用 `DamageResult.TotalDamage = Blocked + Unblocked`；游戏自身 `DamageDealt` 只统计 `UnblockedDamage`。打高格挡敌人时 DPS 偏高。

**判定**

确认（源码），属于统计口径问题。建议明确 UI 说明，或改用未格挡伤害。

## 4. 伤害修正与减伤


### D1. 真实伤害守卫挂错重载，v0.113.1 减伤几乎不入账

**现象**

v0.113.1 中，大多数怪物攻击通过 `DamageCmd.Attack` 结算。无实体、巨像、非虚弱减益、遗物减伤的防御行基本不出现；防御图只剩格挡和虚弱。

**调用链**

1. `AttackCommand.Execute` 用 `targetData:` 调用 `CreatureCmd.Damage`，匹配 `IEnumerable<DamageTargetData>` 根重载：`../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Commands.Builders/AttackCommand.cs:663`。
2. 根重载在 `CreatureCmd.cs:310` 调 `Hook.ModifyDamage`。
3. `RealDamageGuardPatch` 实际绑定的是 `IEnumerable<Creature>` 转发重载：`9.SRC/src/Patches/CombatHistoryPatch.cs:1202-1222`。
4. 根重载没有进入守卫窗口，`EnemyDamageIntentPatch` 在 `:1286` 直接返回。
5. 因此 `OnIntangibleReduction`、`OnColossusMitigation`、`OnDebuffPrevention` 和遗物减伤在 v0.113.1 的 `DamageCmd.Attack` 路径不执行。

**版本差异**

v0.111.1 的 `AttackCommand` 走 `IEnumerable<Creature>` 根重载，7 参数回退能命中，所以旧版本正常。v0.113.1 新增 `IEnumerable<DamageTargetData>` 根重载后，守卫静默失效。

**判定**

确认（源码）。日志里的 `patched 8-param CreatureCmd.Damage` 只能证明绑定了某个 8 参数重载，不能证明它覆盖真实攻击入口。

**建议**

- 改为绑定 `IEnumerable<DamageTargetData>` 根重载，或用 `AsyncLocal<int>` 深度计数覆盖两个重载。
- 增加“怪物攻击 + 无实体”与“怪物攻击 + 巨像”的实机回归。

### D2. 无实体与巨像同时生效时减伤翻倍

**现象**

20 点攻击同时被无实体和巨像减免时，面板可能记 19 + 19 = 38，而实际只减免 19。

**根因**

`AfterModifyDamage_Enemy` 对无实体和巨像都使用 `baseDmg - finalDmg`：`9.SRC/src/Patches/CombatHistoryPatch.cs:1318-1330`。这个差值包含其他修正；两个分支各记一份，`TotalDefense` 又直接求和：`ContributionMap.cs:33`。

**判定**

确认（源码）。当前代码注释说“一行多记不会放大总数”，与总防御求和实现矛盾。

**建议**

按修正链顺序记录每个修正的“前值 - 后值”，不要用最终值反推多个来源。

### D3. 基础伤害未含力量，巨像/无实体少记

`EnemyDamageIntentPatch` 用 `baseDmg` 作为减伤前基准，但 `baseDmg` 是 `Hook.ModifyDamage` 入口值，不含 Additive 力量：`:1290-1291`。敌人有力量时，巨像/无实体的实际边际被低估，甚至直接返回 0。

**判定**

确认（源码）。

### D4. 摧残来源查错表

摧残的易伤加成通过 `GetPowerSource("DEBILITATE_POWER")` 查全局玩家能力表，但敌人的减益只写入 `_creatureDebuffSources`：`9.SRC/src/Patches/CombatHistoryPatch.cs:1144-1160`；`CombatTracker.cs:1128-1145`。因此摧残会显示为裸 `DEBILITATE_POWER`，而不是施放它的卡。

**判定**

确认（源码）。旧运行证据也有裸 `DEBILITATE_POWER` 行，但旧证据只作旁证。

### D5. 力量来源只增不减

`RecordPowerSource` 对玩家力量只增加；`OnPowerApplied` 的负值不记录，`DebuffDurationPatch` 只对易伤/虚弱/中毒减层，肌肉药水过期或玩家失去力量后，旧来源份额仍在。攻击的 `ModifierDamage` 会继续分给已经失效的来源。

**证据**

`9.SRC/src/Patches/CombatHistoryPatch.cs:1443-1463`；`CombatTracker.cs:1118-1126`；`ContributionMap.cs:288-330`。

**判定**

确认（源码）。

## 5. 格挡与承伤


### B1. 回合开始无条件清空格挡池

**现象**

锚的开局格挡、壁垒/残影/坚固钳子保留的格挡，被敌人打掉时没有记到任何来源，防御图偏小。

**调用链**

1. 锚在战斗开始获得 10 格挡，模组把格挡块写入池：`9.SRC/src/Patches/CombatHistoryPatch.cs:194-215`。
2. 第 1 回合 `Creature.AfterTurnStart` 提前返回，格挡实际没有清空：`../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Entities.Creatures/Creature.cs:685-696`。
3. 但 `CombatManager` 仍无条件调用 `Hook.AfterBlockCleared`：`CombatManager.cs:784-791`。
4. 模组 Prefix 直接 `ClearBlockPool()`：`CombatHistoryPatch.cs:99-108`。
5. 受击时 `ConsumeBlockDetailed` 找不到格挡条目，`EffectiveBlock` 不增加。

**判定**

确认（源码）。建议在真正清空 `Block == 0` 时才清池，或排除第 1 回合和 `ShouldClearBlock == false`。

### B2. 未登记上下文的格挡来源落 UNTRACKED

**现象**

旧运行证据中多场战斗出现 `UNTRACKED.EffectiveBlock`；当前代码中仍有多个会获得格挡的能力没有登记上下文：

- 冷却剂
- 盾墙
- 万事无忧
- 歌之道
- 摇篮曲
- 胆小
- 自成型黏土
- 坚韧之环

**证据**

`CombatTracker.cs:527-553`（无来源回退）；`CombatHistoryPatch.cs:970-1010`（格挡入账）；各能力源码。

**判定**

机制确认（源码）。旧 JSON 是旁证，具体来源需当前版本日志确认。

**建议**

把这些 hook 加入能力上下文；`OnBlockGained` 无上下文时按能力 owner 兜底，不要直接落 UNTRACKED。

### B3. 格挡加成列表可能跨玩家残留

`LastBlockModifiers` 是共享列表；`BlockModifierPatch` 只判断 `target.IsPlayer`，多人下队友格挡加成会残留到本机下一次格挡。

**判定**

确认（源码）。建议按 creature hash 分桶，入口过滤本地玩家。

## 6. 抽牌、能量、辉星与费用


### E1. 能量获取记录的是请求值，不是实际获得值

**现象**

当「无法获得能量」等效果把能量获取改成 0 时，贡献图仍可能给来源增加能量；当其他效果修改实际获得量时，数字也会偏离。

**游戏逻辑**

`PlayerCmd.GainEnergy` 先调用 `Hook.ModifyEnergyGain` 得到 `finalAmount`，只在 `finalAmount > 0` 时真正增加能量：`../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Commands/PlayerCmd.cs:29-47`。

**模组代码**

`EnergyGainPatch` 的 postfix 只接收原始 `amount`，没有读取 `finalAmount` 或实际能量差：`9.SRC/src/Patches/CombatHistoryPatch.cs:1573-1585`。

**判定**

## 7. 治疗、最大生命、死亡与复活


### H1. 缩放仪的治疗钩子挂错

**现象**

缩放仪（`PANTOGRAPH`）在 Boss 战开始时治疗 25 点，但当前补丁没有包住这次治疗；贡献表可能把治疗记到楼层恢复，读档重入时还可能重复累计。

**游戏逻辑**

`Pantograph.AfterRoomEntered` 只更新遗物状态；实际治疗在 `BeforeCombatStart`：

```text
../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models.Relics/Pantograph.cs:16
../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models.Relics/Pantograph.cs:27-32
```

**模组代码**

`TryPatch` 把缩放仪挂在 `AfterRoomEntered`：

```text
9.SRC/src/Patches/CombatHistoryPatch.cs:512
```

因此 `CreatureCmd.Heal` 触发时没有缩放仪的 active relic 上下文。`HealingPatch` 会按房间类型回退成 `FLOOR_x_REGEN`：`9.SRC/src/Patches/CombatHistoryPatch.cs:1895-1930`。

**额外风险**

同一个 Boss 战在读档后重新进入 `BeforeCombatStart`，治疗可能再次发生；当前代码没有按“同一场 Boss 战的缩放仪治疗”去重。「浴袍」在 Boss 战开始回满血的路径同样没有上下文，也会落到楼层恢复。

还有第二个层级问题：`HealingPatch` 用 `_currentCombat.Count > 0` 判断是否在战斗中；Boss 战开场治疗发生在 `_currentCombat` 尚空时，会被写入局内总计，而不是本场战斗。

**判定**

确认（源码）。旧 issue 的 `191` 具体数值来自旧游戏版本和多次读档；当前版本不一定复现同一个数字，但归因和重复风险仍在。


**建议**

- 补丁改挂 `BeforeCombatStart`，并同时保留 `AfterRoomEntered` 的状态逻辑。
- 记录 Boss 战标识，保证同一场 Boss 战只计一次缩放仪治疗。
- 增加“Boss 战开始 → 存档 → 读档”的回归测试。

## 9. 能力 hook


### P1. 「黑洞」会抢走辉星来源

**现象**

当玩家同时拥有「黑洞」和「创世纪」「下回合辉星」或「封印王座」时，辉星贡献可能显示为「未归因」，或记到当前正在打出的牌。

**调用链**

1. 「创世纪」在能量重置时调用 `PlayerCmd.GainStars`：`../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Commands/PlayerCmd.cs:90-97`。
2. `GainStars` 先增加辉星，再 `await Hook.AfterStarsGained`。
3. 「黑洞」的 `AfterStarsGained` 补丁先用 `SetPowerContext` 覆盖当前能力来源：`9.SRC/src/Patches/CombatHistoryPatch.cs:840`。
4. 黑洞 hook 首次挂起后，`ClearPowerContext` 把 active power 清空：`:745-750`。
5. `StarsGainedPatch` 的 postfix 这时才执行，`OnStarsGained` 读不到来源：`:1721-1733`。

**判定**

确认（源码）。属于能力上下文被嵌套 hook 清空的实例；玩家在辉星列可见。

**建议**

- 用保存/恢复的上下文栈，或让 `StarsGainedPatch` 在 `GainStars` 内显式捕获来源。
- 黑洞 hook 结束后不能清掉外层的创世纪/封印王座来源。

### P2. 能力 hook 无条件写入待定抽牌来源

`SetPowerContext` 对所有来源可解析的能力 hook 调用 `SetPendingDrawSource`：`9.SRC/src/Patches/CombatHistoryPatch.cs:725-741`。这与 X1 是同一根因，能力侧触发点包括：

- 「紧勒」「子程序」「死亡之舞」「灰烬之灵」「封印王座」的 `BeforeCardPlayed`
- 「自动化」「迭代」「书页风暴」「速行者」的 `AfterCardDrawn`
- 「爆发」「回响形态」的出牌次数修改

其中不少 hook 本身不抽牌，只是布置 pending；下一张非手抽牌会错误记到它们。详见 `TMP/1.5.2/107-audit/slices/08-power-hooks-a.md`、`09-power-hooks-b.md`。

### P3. 多来源格挡能力只记第一个来源

「覆甲」等能力的格挡走单来源 `ResolveSource`，不会像伤害那样按来源比例拆分。护喉甲 + 岩石铠甲 + 铁心药水同时提供覆甲时，整块格挡会记到第一个来源。

**证据**

- `GetPowerSource` 只返回第一个来源：`9.SRC/src/Collection/ContributionMap.cs:278-282`。
- 格挡路径 `OnBlockGained` 没有多来源拆分：`9.SRC/src/Collection/CombatTracker.cs:970-1026`。
- 游戏覆甲按总层数给格挡：`../STS2-Reference/4.STS2-113.1Reference/decompiled/MegaCrit.Sts2.Core.Models.Powers/PlatingPower.cs:61-68`。

**判定**

确认（源码）。当前版本可见，条件是同一玩家同时有两个以上覆甲来源。

### P4. 死补丁与无收益补丁

- `OutbreakPower` 在 v0.111.1、v0.113.1 都不存在；条件式 `TryPatch` 永远跳过：`9.SRC/src/Patches/CombatHistoryPatch.cs:786-788`。毒性爆发的即时中毒伤害因此会落在卡牌自身，而不是中毒来源。
- 「无尽刀刃」的 `BeforeHandDraw` 只生成小刀，不产生抽牌/伤害/格挡贡献；该补丁只有 pending 抽牌副作用：`:795`。
- 第一段两个死/无效补丁是「毒性爆发」的 `OutbreakPower` 与「无尽刀刃」的 `BeforeHandDraw`；其余项目见 `08-power-hooks-a.md`。
- 第二段另有 12 个无归因收益的 patch；详见 `09-power-hooks-b.md`。

**判定**

确认（源码）。这些不是游戏公式错误，属于补丁覆盖与统计口径问题。

### P5. `AccessTools.Method` 可能绑定基类方法

`TryPatch` 使用 `AccessTools.Method(type, methodName)`，它会向基类查找；如果目标类型没有自己的 override，补丁可能落到基类方法上。短版本 `Safe.TryPatchFirst` 使用 `AccessTools.DeclaredMethod`，已避免该问题。

**证据**

- `TryPatch`：`9.SRC/src/Patches/CombatHistoryPatch.cs:911-928`。
- `Safe.TryPatchFirst`：`9.SRC/src/Util/SafePatching.cs:42-63`。
- 当前目标方法在 v0.113.1/v0.111.1 都存在；这是未来版本和维护风险，不是已确认的当前错误。

## 10. 卡牌生命周期、锻造与球


### C1. 能力生成卡没有来源，同名卡与原生卡合并

`CardGenerationOriginPatch.RecordCardOriginInternal` 先拿 `ActivePowerSourceId`（已经是来源卡 ID），随后又用这个来源 ID 调 `GetPowerSource` 查以 **powerId** 为键的表，结果永远查不到：

```text
9.SRC/src/Patches/CombatHistoryPatch.cs:3022-3040
9.SRC/src/Collection/ContributionMap.cs:278-282
```

受影响的能力生成卡包括：

- 光谱偏移
- 创造性AI
- 你好世界
- 虚空之唤
- 哨兵模式

同名生成卡因此与牌库原生卡落到同一个桶，能力父条不显示。

**判定**

确认（源码）。玩家在卡牌/贡献面板可见。

**建议**

直接把 `ActivePowerSourceId` 与 `ActivePowerSourceType` 作为 origin 写入，不要再次按 powerId 查表。

### C2. 药水生成并免费的牌会虚增能量

攻击药水、技能药水先生成一张牌，再让该牌本回合免费。当前代码在生成卡还没有 origin 时就把「免费」标成药水费用减免，打出时会以「牌面费用 - 0」给药水增加能量贡献。

**证据**

- 生成 hook 不读取 `ActivePotionId`：`9.SRC/src/Patches/CombatHistoryPatch.cs:3022-3040`。
- 费用标签逻辑在 origin 缺失时标成药水：`:2204-2249`。
- `MarkCardAsGeneratedAndFree` 只在 `origin == sourceId` 时生效，药水生成卡永远不命中：`ContributionMap.cs:589-597`。

**判定**

确认（源码）。玩家在能量贡献列可见虚增值。

### C3. 升级格挡被双计

原卡获得 8 格挡时，`OnBlockGained` 先把 8 全部记给原卡，随后又把升级增量 3 记给升级来源。总防御因此变成 11，而游戏实际只有 8。

**证据**

- `OnBlockGained` 先 `AddBlock` 满额，再写 `UpgradeBlock`：`9.SRC/src/Collection/CombatTracker.cs:970-1027`。
- 伤害路径会从 `directDamage` 扣除升级增量，格挡路径没有扣。

**判定**

确认（源码）。防御总览和百分比会虚高，即使格挡没有被消耗也会出现。

**建议**

格挡块按 `baseAmount - upgSplit` 记给原卡，只把 `upgSplit` 记给升级来源；或按实际消耗比例拆分。

### C4. 升级只统计伤害/格挡两个变量

`CardUpgradeTrackerPatch` 只读 `DynamicVars["Damage"]` 与 `["Block"]`：`9.SRC/src/Patches/CombatHistoryPatch.cs:1636-1644`。升级段数、附加伤害、计算伤害等不会产生升级来源贡献。

受影响例子：

- 完美打击的 `ExtraDamage`
- 和声之盾的 `CalculationExtra`
- 飞剑回旋镖的 `HitCount`
- 天穹之力、连续反弹、啄击、迅捷射击、怨恨等同类卡

**判定**

确认（源码）。升级来源低报；当前卡面伤害仍记在卡牌本身。

### C5. 多次升级只保留最后一次增量

`RecordUpgradeDelta` 以卡牌哈希为键覆盖写，不是累加：`ContributionMap.cs:911-918`。黯淡匕首可连续升级多次，升级来源只记录最后一次增量。

**判定**

确认（源码）。黯淡匕首连续升级后，升级来源低估。

### C6. 君王之剑锻造子条翻倍

`FlushForgeSubBars` 每次打出君王之剑都遍历 `_forgeLog`，但从不消费日志：`9.SRC/src/Collection/CombatTracker.cs:1529-1565`。第二次打出时同一批锻造来源再次累加；父条本身已包含锻造伤害，图表分母又把子条加一遍。

**判定**

确认（源码）。玩家可直接看到子条随打出次数翻倍，总伤害百分比超过 100%。

**建议**

每次 Flush 后消费日志；子条只作为父条分解，不再进入总分母。

## 11. 跨切片问题

这一节记录不属于单个遗物/能力 hook，而是影响整张贡献表的共享状态问题。

### X1. 抽牌待定来源没有清理

**现象**

某次遗物或能力 hook 触发后，下一次非手牌抽牌可能被记到该遗物/能力，而不是实际来源。该错误可以跨回合、跨战斗出现。

**代码证据**

- `SetRelicContext` 对每个遗物 hook 都调用 `SetPendingDrawSource`：`9.SRC/src/Patches/CombatHistoryPatch.cs:274-282`。
- `ClearRelicContext` 只清 `ActiveRelic`，不清 pending draw：`:287-290`。
- `SetPowerContext` 同样为所有已解析来源的能力 hook 设置 pending draw：`:725-740`；`ClearPowerContext` 只清 active power：`:745-753`。
- `OnCardDrawn` 如果看到 pending source，直接消费并返回，不校验这次抽牌是否由该来源产生：`9.SRC/src/Collection/CombatTracker.cs:1202-1229`。
- `OnCombatStart` 和 `OnCombatEnd` 都没有清理 pending draw：`CombatTracker.cs:312-359`。
- `ClearPendingDrawSource` 已定义，但全仓没有调用点：`CombatTracker.cs:1195-1200`。

**具体调用链**

1. 「燃烧之血」在战斗胜利后触发，`SetRelicContext` 设置 pending source 为 `BURNING_BLOOD`。
2. 该 hook 不抽牌；pending 保持。
3. 下一场战斗中使用「打击」以外的抽牌卡，例如「剑柄打击」的额外抽牌。
4. `OnCardDrawn(fromHandDraw=false)` 直接消费 pending，把这次抽牌记到「燃烧之血」。
5. 实际来源卡牌少记一次抽牌，「燃烧之血」多记一次。

同样路径可发生在「小血瓶」「锁镰」「缩放仪」等不抽牌的遗物 hook 上。

**判定**

确认（源码调用链）。影响贡献图的抽牌来源；不会改变实际抽牌数量。

**建议**

- 只在已知会抽牌的 hook 上设置 pending draw。
- 在 `ClearRelicContext`、`ClearPowerContext` 里恢复/清理 pending draw，不能让它跨 hook、跨回合、跨战斗。
- 在 `OnCombatStart`、`OnCombatEnd`、`OnTurnStart` 清理 pending draw。
- 对 N 次抽牌的 hook，如果实际抽牌数不足，必须在回合结束时丢弃剩余计数。
- 增加“触发不抽牌的遗物 hook，再用另一张卡抽牌”的回归测试，断言抽牌归到实际卡牌。

### X2. 嵌套 hook 会覆盖外层来源

**代码证据**

- `SetRelicContext` 直接覆盖当前 `_activeRelicId`；`ClearRelicContext` 直接置空，没有保存/恢复外层值：`9.SRC/src/Patches/CombatHistoryPatch.cs:266-290`。
- `PowerHookContextPatcher` 使用同一单槽模式：`:664-753`。
- 这属于 `3.DOCS/018-R-全面系统性审阅.md` 的 P3-20，当前代码仍未改成栈式上下文。

**判定**

高风险（源码确认结构，具体玩家可见场景未逐条实跑）。当遗物 A 的 hook 内触发遗物 B，或能力 A 的 hook 内触发能力 B 时，B 的 postfix 会把外层来源清空，A 在 B 返回后的后续效果可能落到 `UNTRACKED` 或错误来源。

**建议**

- 使用 `AsyncLocal<ImmutableStack<SourceContext>>`，或保存旧值并在 postfix 恢复。
- 对嵌套触发建立测试：外层遗物/能力 → 内层遗物/能力 → 外层后续伤害/抽牌/治疗。

### X3. `RealDamageGuard` 使用线程静态布尔值

**代码证据**

- `RealDamageGuardPatch.IsInsideCreatureDamage` 是 `[ThreadStatic] bool`：`9.SRC/src/Patches/CombatHistoryPatch.cs:1184-1240`。
- 游戏的多目标 `CreatureCmd.Damage` 会异步循环目标；Harmony postfix 在首次挂起后清除守卫。
- 这属于 `3.DOCS/018-R-全面系统性审阅.md` 的 P2-20，当前代码仍未改成深度计数。

**判定**

确认（源码）。多目标/AoE 的后续目标可能不在守卫窗口内，导致无实体、巨像、敌方减益等减伤行漏记。

即使 D1 的根重载修复，`[ThreadStatic]` 仍会在第一个 `await` 后失效；两项必须一起改。


**建议**

- 使用 `AsyncLocal<int>` 深度计数，而不是 `[ThreadStatic] bool`。
- 或改为从 `CombatHistory.DamageReceived`/`DamageResult` 读取真实减伤。
- 增加多目标 AoE 的防御归因测试。

### X4. 名称匹配不校验重载

`TryPatch` 使用 `AccessTools.Method(type, methodName)`，只按方法名取目标，不传参数类型：`9.SRC/src/Patches/CombatHistoryPatch.cs:638-655`、`:911-929`。当前审计确认所有目标方法名都能在 v0.113.1 和 v0.111.1 找到，但不能证明绑定的是正确重载。若某个 hook 同时有多个重载，Harmony 可能绑定第一个，补丁静默失效或记错事件。

**判定**

高风险（结构性问题，具体重载未确认）。建议在 `TryPatch` 中逐步改成显式参数类型，至少对已知多重重载的目标这样做。

### X6. 战斗失败不结算，最终战贡献丢失

**现象**

玩家死亡的那场战斗没有进入本局汇总；跑团历史/生涯统计缺少死亡战样本，`PlayerDied` 一直为 false。

**根因**

模组只 patch `CombatRoom.OnCombatEnded`：`9.SRC/src/Patches/CombatLifecyclePatch.cs:72-99`。游戏失败路径 `ProcessPendingLoss` 触发 `CombatManager.CombatEnded` 事件，不调用 `room.OnCombatEnded()`：`CombatManager.cs:1357-1367`。

**判定**

确认（源码）。建议订阅 `CombatManager.CombatEnded`，失败时走同一套 `OnCombatEnd` + 落盘。

### X7. `AfterCardPlayed` 未登记的能力/遗物落 UNTRACKED

`CardPlayFinished` 早于 `Hook.AfterCardPlayed`；模组的 `CardPlayFinished` postfix 先清空 `_activeCardId`：`CombatHistoryPatch.cs:81-95`；`CardModel.cs:2130-2134`。

如果某个 `AfterCardPlayed` 能力/遗物没有自己的上下文补丁，效果发生时没有任何来源。已知未登记的例子：

- 引力
- 暴力和弦
- 曲中意
- 失落鲁特琴
- 歌之道
- 胆小
- 摇篮曲

**判定**

确认（源码）。建议补齐这些 hook，或把 `_activeCardId` 的清理推迟到 `Hook.AfterCardPlayed` 之后。

### X8. 减伤/修正的跨切片重复

### X9. 文档计数：107 不是 107 个方法

`107` 是 `CombatHistoryPatch.cs` 中的 `[HarmonyPatch]` 特性数：31 个类级 + 76 个方法级。实际注册目标远多于 107：
