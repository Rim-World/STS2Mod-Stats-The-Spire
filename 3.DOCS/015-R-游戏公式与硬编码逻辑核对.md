- 时间：2026-11-20 05:27
- 审计对象：`9.SRC/src` 中显示值的游戏规则来源
- 游戏基准：`STS2-Reference/4.STS2-113.1Reference/decompiled`（v0.113.1，提交 `d09d48e5`）
- 对照版本：`STS2-Reference/2.STS2-111Reference/decompiled`（v0.111.1）
- 审计方式：源码逐项对照。未启动游戏，未做悬停实机验证。
- 官中术语与玩家可见性改写版：`3.DOCS/016-R-游戏规则官中术语与玩家可见性.md`。

## 1. 结论摘要

本 Mod 真正依赖游戏数学规则的显示，集中在四类概率/价格面板、意图状态机和古代遗物池。按代码行数粗略统计，直接相关的代码约 3,600 行；其余大量代码是游戏事件提取、贡献归因和本地历史统计，不是游戏公式复刻。

最重要的结论：

1. 卡牌掉落面板在 A7+「稀缺」进阶下使用了错误的基础概率。面板固定为 `3% / 37% / 10% / 40%`，没有读取 `CardRarityOdds` 的进阶值。
2. 卡牌面板把 `CardRarityOdds.CurrentValue` 的负偏移只用于稀有牌，导致初始状态和稀有牌重置后的「罕见/普通」分配错误。即使 A0 也错。
3. 卡牌面板显示的是「单张卡」的概率，但界面副标题写「各稀有度至少出现一张」。下一场战斗的卡牌奖励通常是 3 张，二者不是同一个量。
4. 问号房间面板没有使用 `RunManager.BuildRoomTypeBlacklist`。当上一个房间是商店，或后续所有节点都是商店时，游戏禁止问号出商店，面板仍显示商店概率。
5. 问号房间面板没有处理新档前两个问号的固定结果：第一个和第二个都固定事件，第三个固定怪物。
6. v0.113 新增 Blitz 模式后，卡牌、药水、商店三个面板仍按标准模式解释：
   - Blitz 普通战斗固定给普通卡，精英固定给罕见卡，Boss 固定给稀有卡；面板仍显示概率表。
   - Blitz 普通非弱怪战斗直接给 `PotionReward`，不按药水概率滚动；面板仍显示概率。
   - Blitz 商店条目价格为 0；面板仍显示标准商店价格。
7. 商店价格表遗漏了 `RelicRarity.Shop` 的 200 金遗物，也遗漏了每个标准商店固定有一张半价角色牌。
8. 意图面板的百分比是「设计基础权重」，不是当前回合的实际有效概率；`CannotRepeat`、`UseOnlyOnce`、冷却、状态历史没有参与百分比计算。
9. 意图攻击图标按「单次伤害」选档，游戏按「总伤害」选档；多段攻击的图标会偏低。
10. 意图伤害数字直接使用 `DamageCalc()` 的原始值，没有走游戏的 `GetSingleDamage` / `Hook.ModifyDamage`；敌人有力量、虚弱、易伤等修正时数字不一致。
11. Neow 静态池把 `SCROLL_BOXES` 和 `SILKEN_TRESS` 放反；动态补充只修正后者，前者仍按错误池统计。
12. Wriggler 的 `SPAWNED_MOVE` 后继被强制成 BITE，实际槽位 2/4 应进入 WRIGGLE。
13. 持有 White Beast Statue 时药水实际 100%，面板未读取强制药水钩子。
14. 首次挂载和开关开启时，药水/卡牌指示器可能停在占位值，直到下一次刷新。
15. 古代池有三处错位：`SEAL_OF_GOLD` 应在 Tezcatara 池 3、`SAND_CASTLE` 应在 Orobas 池 2；`SEA_GLASS` 的带角色 ID 使该遗物统计长期为 0。
16. Darv 把 11 个遗物组压成 12 个等权成员；Neow 手写表缺 7 项，且 `SCROLL_BOXES` 错放在诅咒池。
17. 长老中文名有 4 个与官方不一致；Boss 幕号表假设的幕顺序也错。
18. 意图图还有 Myte/Phantasmal Gardener 初始条件框丢失、Terror Eel 死状态、Scroll/Chomper 初始标签错误、Test Subject 断边和 Queen 部分覆写。

没有发现 v0.111.1 → v0.113.1 对药水、问号、卡牌基础数值或普通商店价格做过数值改动。`PotionRewardOdds.cs` 和 `UnknownMapPointOdds.cs` 在两个版本中内容相同；`CardRarityOdds` 的数值常量未变，只新增了 Blitz 类型和 RNG 参数；普通商店的卡牌、遗物、药水、删牌价格未变。因此：

- 绝大多数「过时/错误」不是 0.113 造成的，而是原本的近似、遗漏或错误假设。
- 唯一明确的 0.113 新缺口是 Blitz 模式。
- 内容表漂移（Darv、Neow、Nibbit）属于长期维护风险，不是 113 数值公式改动。

## 3. 药水掉落

### 3.1 当前值和精英概率

| 项目 | Mod | 游戏 | 判定 |
|---|---|---|---|
| 当前概率 | `PotionOddsIndicator.cs:107-111` 读取 `PotionReward.CurrentValue`，显示一位小数 | `PotionRewardOdds.cs:55-70` | 正确 |
| 精英加成 | `PotionOddsIndicator.cs:143` 加 `0.125` | `PotionRewardOdds.cs:62-63`：`eliteBonus 0.25 * 0.5` | 正确 |
| 基础值 | 不硬编码，读运行时 | `_basePotionRewardOdds = 0.4` | 正确 |
| 中奖后下调 | 不自行计算 | 每次中奖 `CurrentValue -= 0.1` | 正确 |

### 3.2 累计概率

`PotionOddsIndicator.CumulativeOdds`（`PotionOddsIndicator.cs:118-129`）按「接下来 N 场全部未中奖」计算：

- 第 i 场概率 `p = current + 0.1 * i`。
- 中奖概率的补集连乘。
- 这对「非精英、无强制掉落、全部未中奖」的条件是正确的。
- 参数 `anyElite` 会把 `0.125` 加到每一场；如果它的含义是「N 场里至少有一场精英」，这是错的；如果含义是「N 场全部是精英」，才是对的。
- 当前唯一调用点 `PotionOddsIndicator.cs:159` 固定传 `false`，所以该错误暂未暴露；它是潜在缺陷，不是当前显示错误。
- 面板没有说明「累计行假设全部是普通战斗」。这是信息缺失，不是数值错误。

### 3.3 负当前值被截断

`UpdateOdds` 在 `PotionOddsIndicator.cs:109` 把 `CurrentValue` 夹到 `[0,1]`。游戏 `AbstractOdds` 和 `PotionRewardOdds` 没有这个下限。

当当前值为负时，例如 `-0.1`：

- 普通战斗实际概率为 0；面板显示 0，正确。
- 精英战斗实际概率为 `-0.1 + 0.125 = 2.5%`；面板先夹成 0，再加 `0.125`，显示 `12.5%`。高估 10 个百分点。
- `CumulativeOdds` 也从 0 而不是 `-0.1` 起步，后续累计会前移一场。

负值可以通过「当前值为 0 时打精英并掉药水」产生，因为游戏在命中后直接减 0.1。该问题为中等严重度，属于边界状态。

### 3.4 White Beast Statue 未建模

游戏 `PotionRewardOdds.Roll` 在正常滚骰前执行：

```csharp
if (Hook.ShouldForcePotionReward(...)) return true;
```

`WhiteBeastStatue` 是唯一的 Vanilla 实现（`WhiteBeastStatue.cs:11-22`）：在战斗房间（Monster/Elite/Boss）返回 true，且**不修改** `CurrentValue`。

Mod 面板只读取 `CurrentValue`，没有读取这个钩子。持有 White Beast Statue 时：

- 实际每场战斗 100% 掉药水。
- 面板仍显示 40% 到 90% 的递增曲线。
- 累计表也按普通概率计算，完全错误。

这是药水面板最高优先级的遗漏之一。

### 3.5 首次挂载和开关刷新时序

`CombatUiOverlayPatch.TryAttachDeferred`（`CombatUiOverlayPatch.cs:100-108`）的顺序是：

1. `EnsureAttachedToTopBar()` 创建两个指示器，初始 `Visible=false`，药水标签为 `"—"`。
2. `RefreshValuesFromPlayer()` 检查 `Visible` 后直接跳过，因为此时还是 false。
3. `ShowAll()` 把指示器设为可见。

因此首次挂载后：

- 药水指示器停留在 `"—"`，`_currentOdds` 仍为 0。
- 卡牌指示器没有标签，但 `_currentOffset` 仍为 0，悬停表按「零偏移」而不是 `-0.05` 计算。
- 直到下一次战斗事件刷新才会修正。

`RefreshVisibility`（`:367-374`）只改 `Visible`，不重新拉取数值。中途从设置页打开开关时，也会出现同样的 `"—"`/零值悬停。

### 3.6 刷新时序与奖励

`CombatRoom.OnCombatEnded` 的 postfix 在 `OfferRoomEndRewards()` 之前刷新。药水和卡牌的 `Roll` 发生在奖励生成时，因此奖励界面期间面板显示的是「刚用过的那次」数值，下一场数值要等地图打开或下一次战斗刷新。进入下一场战斗前通常会修正；如果用户在奖励界面悬停，会看到旧值。

这属于时序问题，不是公式数值错误，但会造成短时间误导。

## 4. 卡牌掉落

### 4.1 基础概率

Mod 在 `CardDropOddsIndicator.cs:22-26` 固定：

```text
RegularRareBase = 0.03
RegularUncommonBase = 0.37
EliteRareBase = 0.10
EliteUncommonBase = 0.40
```

游戏 `CardRarityOdds.cs` 的值：

| 来源 | 普通战斗稀有 | 普通战斗罕见 | 精英稀有 | 精英罕见 |
|---|---:|---:|---:|---:|
| A0-A6 | 0.03 | 0.37 | 0.10 | 0.40 |
| A7+「稀缺」 | 0.0149 | 0.37 | 0.05 | 0.40 |

`CardRarityOdds.cs:13-49` 通过 `AscensionHelper.GetValueIfAscension(AscensionLevel.Scarcity, ...)` 选择。Mod 没有读取这些静态属性，也没有检查 `RunManager.HasAscension(Scarcity)`。

用户当前使用 A10，因此该面板在普通战斗和精英战斗都显示错误基础值。

### 4.2 偏移语义

游戏 `RollWithoutChangingFutureOdds`（`CardRarityOdds.cs:110-125`）：

```text
rareThreshold     = baseRare + offset
uncommonThreshold = baseUncommon + rareThreshold
若 roll < rareThreshold       -> Rare
否则若 roll < uncommonThreshold -> Uncommon
否则                            -> Common
```

所以当 `rareThreshold` 为负时：

- 稀有概率为 0。
- 罕见概率不是固定的 `baseUncommon`，而是 `baseUncommon + rareThreshold`。
- 剩余给普通。

Mod 在 `CardDropOddsIndicator.cs:119-124` 固定 `regularUncommon = 0.37`，只在稀有概率上应用偏移，剩余全部给普通。这导致：

| 状态 | 游戏（普通/罕见/稀有） | Mod（普通/罕见/稀有） |
|---|---|---|
| A0 初始 `offset=-0.05` | 65.00% / 35.00% / 0% | 63.00% / 37.00% / 0% |
| A7+ 初始 `offset=-0.05` | 66.51% / 33.49% / 0% | 63.00% / 37.00% / 0% |
| A7+ `offset=0` | 61.51% / 37.00% / 1.49% | 60.00% / 37.00% / 3.00% |
| A7+ 精英初始 | 60.00% / 40.00% / 0% | 55.00% / 40.00% / 5.00% |
| A7+ 精英 `offset=0` | 55.00% / 40.00% / 5.00% | 50.00% / 40.00% / 10.00% |

结论：

- 初始状态即使 A0 也错：普通 63 对 65，罕见 37 对 35。
- A7+ 所有状态都错，因为基础值也未切换。
- 该问题直接违反面板「各稀有度概率」的语义。

### 4.3 「至少出现一张」与「单张概率」

`Localization.cs:145` 和 `:474` 的副标题分别写：

```text
Probability of at least one per rarity
各稀有度至少出现一张的概率
```

但 `CardDropOddsIndicator.cs:119-129` 只计算单张卡的概率。`CardReward` 默认提供 3 张选择（`CardReward.cs:114-118`），`CardFactory.CreateForReward` 逐张生成（`CardFactory.cs:90-109`）。

因此：

- 普通战斗 A0 `offset=0` 的稀有单张概率是 3%；3 张里至少一张稀有约为 `1 - 0.97^3 = 8.7%`（不考虑保底偏移变化）。
- 精英战斗 A0 `offset=0` 的稀有单张概率是 10%；3 张里至少一张约为 27.1%。
- 面板显示 3% / 10%，但副标题承诺的是 8.7% / 27.1% 这一类的量。

这里至少有一个错误：要么数据应改为「至少一张」，要么副标题应改为「单张」。当前实现是单张。

### 4.4 Boss 和 Blitz

- 面板只有 `Regular` 和 `Elite` 两列；Boss 奖励是 `CardRarityOddsType.BossEncounter`，固定稀有（`CardRarityOdds.cs:164-169`）。Boss 战前的面板没有 Boss 列，显示的不是下一场实际奖励。
- Blitz 模式普通战斗固定给普通卡，精英固定给罕见卡，前两幕 Boss 固定给稀有卡（`BlitzRunModel.cs:90-115`）。面板仍显示标准概率表，完全不适用。
- `BigGameHunter` 修改器会把精英战斗的卡牌奖励改成 `Uniform` 且只允许稀有牌（`BigGameHunter.cs:34-58`），实际精英奖励 100% 稀有。面板仍显示 10% 精英稀有（A0）或 5%（A7+）。这是自定义修改器场景，优先级低于常规 A7+/Blitz，但属于同类缺口。

## 5. 商店价格

### 5.1 基础价格

| 类别 | Mod 值 | 游戏值 | 判定 |
|---|---|---|---|
| 遗物 Common/Uncommon/Rare | 175 / 225 / 275，±15% | `RelicModel.MerchantCost` 175 / 225 / 275，±15% | 正确 |
| 遗物 Shop | 未显示 | 200，±15% | **缺失** |
| 卡牌 Common/Uncommon/Rare | 50 / 75 / 150，±5% | `MerchantCardEntry.GetCost` 50 / 75 / 150，±5% | 正确 |
| 无色卡 | 仅注释「+15%」 | 基础价 ×1.15，四舍五入 | 提示正确，但未给数值 |
| 药水 Common/Uncommon/Rare | 50 / 75 / 100，±5% | `MerchantPotionEntry.GetCost` 50 / 75 / 100，±5% | 正确 |

### 5.2 每个标准商店固定有的两个例外

`MerchantInventory.cs:192-205` 每个标准商店生成 3 个遗物：

```text
两个随机 Common/Uncommon/Rare
一个固定 RelicRarity.Shop（MerchantCost = 200）
```

`MerchantInventory.cs:160-164` 还会把一个角色牌设为 `SetOnSale()`，`MerchantCardEntry.cs:120-125` 将它半价。

`ShopPricePanel.cs:70-80` 的表没有 Shop 行，也没有半价提示。因此：

- 商店必有一个 200 金遗物，面板不显示。
- 商店必有一张半价角色牌，面板只显示 50/75/150 的普通区间。
- 这两项是标准商店的固定结构，不是随机偶发。

### 5.3 折扣

`ShopPricePanel.cs:88-102` 手动识别：

- `MembershipCard`：×0.5。
- `TheCourier`：×0.8。
- 两者叠乘。

v0.113.1 的 `Hook.ModifyMerchantPrice` 会遍历所有模型的价格修改器（`Hook.cs:1881-1887`）。当前 Vanilla 只有这两个遗物覆盖该方法，所以当前版本的结果基本正确。风险是未来新增价格修改遗物时会漏算。

### 5.4 舍入

游戏 `MerchantEntry.Cost` 在 `MerchantEntry.cs:25-30` 用 `decimal` 应用折扣，然后直接转 `int`，即截断。Mod 在 `ShopPricePanel.cs:130-131` 和 `:165` 用 `Math.Round`。

示例：基础删牌费 75，MembershipCard 五折：

- 游戏：`75 * 0.5 = 37.5`，转 `int` 得 37。
- 面板：`Math.Round(37.5)`，默认银行家舍入得 38。

所以面板可能比实际价格高 1 金。价格区间也可能有同类 1 金误差。

### 5.5 删牌状态与多人

- `ShopPricePanel` 总是显示删牌费用；没有检查 `MerchantCardRemovalEntry.Used` 或 `ShouldAllowMerchantCardRemoval`。已使用或不可用时，游戏界面可能没有该服务，面板仍显示。
- `MapPointPatch.cs:56` 和 `:81` 使用 `Players.FirstOrDefault()`。多人游戏中本地玩家不一定是第一个；金币、折扣和删牌次数可能取错玩家。单人无影响。

### 5.6 Blitz 商店

v0.113 的 Blitz 商店使用 `MerchantInventory.CreateForBlitzMerchant`，条目是 `BlitzMerchantEntry`，`Cost => 0`（`BlitzMerchantEntry.cs:110-112`）。Blitz 地图确实有商店节点（`BlitzActMap.cs:10-18`），`MapPointPatch` 也会显示面板。

面板仍显示标准价格表，且显示删牌费用。实际 Blitz 商店是免费选择，价格表完全不适用。

`ShopPatch` 也只补丁 `MerchantCardEntry`、`MerchantRelicEntry`、`MerchantPotionEntry`（`ShopPatch.cs:90-99`），没有补丁 `BlitzMerchantEntry`。Blitz 购买不会进入本地商店购买统计。这不是公式错误，但属于 0.113 新模式的功能缺口。

## 6. 问号房间

### 6.1 已正确处理的部分

`UnknownRoomPanel.cs:34-51` 读取运行时的 `UnknownMapPointOdds`，并通过 `Hook.ModifyUnknownMapPointRoomTypes` 处理：

- 佛珠手链移除怪物；v0.113.1 还额外移除精英。Mod 读取钩子，所以两版都能正确反映。
- 金罗盘、灯笼钥匙强制事件。
- 寻水卡在满足条件后移除怪物/精英。
- 事件概率按剩余正概率计算。

这些方向与游戏一致。

### 6.2 没有使用商店黑名单

`RunManager.cs:724-729` 的 `BuildRoomTypeBlacklist` 规定：

- 上一个房间有商店时，下一个问号不能出商店。
- 当前节点的所有子节点都是商店时，问号不能出商店。

`RunManager.cs:993-994` 在真正滚动前调用这个黑名单。`MapPointPatch.cs:68-73` 只把 `odds` 和 `runState` 传给 `UnknownRoomPanel`，没有传黑名单；面板也没有自行计算。

因此当商店被禁止时：

- 游戏把商店概率从滚动中排除，剩余概率给事件。
- 面板仍显示商店概率，事件概率偏低。

这是当前实际会发生的错误。

### 6.3 新档前两个问号

`UnknownMapPointOdds.cs:125-136` 规定，`UnlockState.NumberOfRuns == 0` 时按**此前已访问的未知房数量**判断：

- 计数 `< 2`：强制事件。
- 计数 `== 2`：强制怪物。

因此新档的前两个问号都是 100% 事件，第三个问号是 100% 怪物。`UnknownRoomPanel` 没有检查 `NumberOfRuns` 或问号历史，仍显示基础概率。新档玩家会看到错误面板。

### 6.4 边缘：事件被排除

如果某个效果把 `Event` 从可选集合移除，`UnknownMapPointOdds.Roll` 会把剩余概率落到第一个可选非事件类型（`UnknownMapPointOdds.cs:139`）。面板把事件概率固定为 0，不显示这部分残余。当前 Vanilla 没有发现移除 Event 的效果，所以是低优先级边缘问题。

### 7.1 数据结构基本正确

`MonsterIntentMetadata` 从运行时 `MoveStateMachine` 读取状态、分支、意图，`MonsterConditionHints` 覆盖了 v0.113.1 中全部 16 个使用 `ConditionalBranchState` 的怪物：

Toadpole, Exoskeleton, Lagavulin Matriarch, Wriggler, Test Subject,

已核对正确的项：

- Toadpole 的 2 号位/1 号位顺序。
- Exoskeleton 的 1-4 号位；4 号位在 3 槽遭遇中会多显示。
- Wriggler 的 1-4 号位。
- Test Subject 的复活次数标签正确，但 `RESPAWN_MOVE` 没有静态入边，见 7.8。
- Lagavulin 和 Slumbering Beetle 的睡眠/苏醒。
- Queen 的组合体存活/死亡标签正确，但死亡分支被部分覆写，见 7.8。
- Ovicopter、Living Shield、Knowledge Demon、Frog Knight、Bowlbug Rock。
- Phantasmal Gardener 和 Myte 的条件标签顺序正确，但初始条件框没有进入 `States`，标签实际不会显示，见 7.8。
- Fabricator 的「机器人 ≤2 / ≥3」：游戏 `GetTeammatesOf` 包含 Fabricator 自身，`<4` 等于最多 2 个机器人，标签正确。

- Wriggler 和 Queen 的硬编码状态 ID 与 v0.113.1 一致；Wriggler 有一条后继被强制改写，见 7.2。
- `_phase1Blocklist = { FABRICATOR }` 仍有依据：Fabricator 是嵌套 `Conditional → Random`，通用 phase 1 无法正确展开；这不是失效代码。

### 7.2 Wriggler 的 SPAWNED 后继被强制成 BITE

游戏 `Wriggler.cs:51-70`：

- `SPAWNED_MOVE.FollowUpState = INIT_MOVE`。
- `INIT_MOVE` 根据槽位选择：`wriggler1/3 -> NASTY_BITE_MOVE`，`wriggler2/4 -> WRIGGLE_MOVE`。
- 被感染的 Wriggler 由 `InfestedPower` 在四个槽位生成，`StartStunned = true`，所以都会经过 `SPAWNED_MOVE -> INIT_MOVE`。

Mod 在 `MonsterIntentMetadata.cs:523-537` 把 `SPAWNED_MOVE.FollowUpStateId` 直接改成 `NASTY_BITE_MOVE`，并隐藏 `INIT_MOVE`。这会丢掉槽位 2/4 的 WRIGGLE 分支：

- 面板对所有被感染的 Wriggler 都显示 `SPAWNED -> BITE`。
- 实际槽位 2/4 是 `SPAWNED -> WRIGGLE`。

`MonsterInitialVariants` 的「1/3 号位」「2/4 号位」标签只解决了初始标签，没有修正图边。该问题为中等严重度，属于意图图逻辑错误。

### 7.3 Nibbit 独自一人标签错误

`MonsterConditionHints.cs:25`：

```text
NIBBIT = [背面, 正面, 独自一人]
```

游戏 `Nibbit.cs:76-85`：

- `_isAlone == true` 时只有一个分支 `BUTT_MOVE`。
- `_isAlone == false` 时有两个分支：`HISS_MOVE`（背面）、`SLICE_MOVE`（正面）。

`MonsterConditionHints.Get` 按分支索引取标签。因此：

- 成对 Nibbit：索引 0=背面，1=正面，正确。
- 独自 Nibbit：索引 0 被标成「背面」，实际应标「独自一人」。第三个标签永远不会被使用。

这是内容标签错误，影响一个弱怪变体。

### 7.4 百分比是基础权重，不是当前有效概率

`MonsterIntentMetadata.cs:584-604` 明确使用 `sw.GetWeight()` 的裸 lambda 值，而不是游戏 `RandomBranchState.GetStateWeight` 的有效值。`IntentStateMachinePanel.cs:1309-1310` 只把这些裸权重归一化。

游戏 `RandomBranchState.GetStateWeight`（`RandomBranchState.cs:130-151`）还会应用：

- `UseOnlyOnce`：已使用则权重 0。
- `CannotRepeat`：连续使用限制。
- `CanRepeatXTimes(N)`：连续次数限制。
- `Cooldown`：冷却期内权重 0。

所以面板显示的百分比是「设计基础分布」，不是当前回合真实概率。界面没有明确说明这一点。对于刚用过不可重复招式的怪物，面板可能显示 50%，实际是 0%。例如 Inklet 刚出过 `JAB_MOVE` 后，游戏会把 `JAB` 过滤为 0，实际 `WHIRLWIND` 100%；面板仍显示 50/50。

### 7.5 `CannotRepeat` 标注误导

`IntentStateMachinePanel.cs:1406-1407` 把 `CannotRepeat` 显示为 `≤1`。

游戏语义是「不能连续使用」，不是「整场只能用一次」。`UseOnlyOnce` 才是整场一次，已经显示为 `×1`。因此 `≤1` 容易被读成「最多一次」。数值过滤本身与游戏一致，问题在文案，应改为「不连用」之类的明确文字。

### 7.6 攻击图标档位错误

`IntentIconCache.cs:116-122` 使用 `5/10/20/40` 阈值，和游戏 `AttackIntent.GetTexture` 的阈值相同（`AttackIntent.cs:42-48`）。但 Mod 传入的是单次伤害：

```csharp
IntentIconCache.GetIcon(info.IntentInstance, info.Damage ?? 0)
```

`IntentStateMachinePanel.cs:1426`；`info.Damage` 来自 `AttackIntent.DamageCalc()` 的单次值（`MonsterIntentMetadata.cs:668-680`）。

游戏使用 `GetTotalDamage`：

- `SingleAttackIntent`：单次伤害，含 `Hook.ModifyDamage`。
- `MultiAttackIntent`：单次伤害 × 重复次数（`MultiAttackIntent.cs:30-32`）。

例子：5×5 的多段攻击，游戏按总伤害 25 选择 3 档图标；Mod 按单次 5 选择 2 档图标。多段攻击会显示偏低的攻击强度图标。

### 7.7 意图伤害数字错误

`IntentStateMachinePanel.cs:1454-1459` 显示：

```text
Damage × Repeats
```

`Damage` 来自 `DamageCalc()` 原始值。游戏预览使用 `AttackIntent.GetSingleDamage`（`AttackIntent.cs:84-93`）：

- 调用 `Hook.ModifyDamage`。
- 应用力量、虚弱、易伤等修正。
- 再取整并下限 0。

因此当敌人有力量、玩家有虚弱/易伤、或其他伤害修正时，面板数字与游戏意图数字不一致。多段攻击的每段数字和总伤害也可能同时错。

### 7.8 其他意图数据问题

**Myte 和 Phantasmal Gardener 的初始条件框没有进入 `States`**

- `Myte.cs:46-61` 创建 `INIT_MOVE`，但只把三个 Move 加入 `list`，`INIT_MOVE` 作为 `initialState` 传入，不在 `list`。
- `PhantasmalGardener.cs:96-116` 同样没有把 `INIT_MOVE` 加入 `list`。
- `MonsterMoveStateMachine` 只注册 `list` 中的状态，`MonsterIntentMetadata` 遍历 `sm.States` 时看不到 `INIT_MOVE`。
- 面板的 `startId` 会回退到第一个 Move，因此把 Myte 的 `TOXIC_MOVE`、Gardener 的 `BITE_MOVE` 当成初始；`MonsterConditionHints` 的 1/2 号位、1-4 号位标签完全不会显示。

这是两个怪物变体的高优先级显示错误。

**Terror Eel 的 `STUN_MOVE` 是死状态**

- `TerrorEel.cs:73` 创建 `STUN_MOVE`，但没有任何 `FollowUpState` 指向它；初始是 `CRASH_MOVE`。
- 真正触发时，`ShriekPower.cs:27-30` 调用 `CreatureCmd.Stun(..., TerrorState.StateId)`；`Creature.cs:537-541` 创建一个临时 `STUNNED` 状态，`FollowUpStateId = TERROR_MOVE`，不是 `STUN_MOVE`。

**Scroll of Biting 的初始标签不是号位**

- `ScrollOfBiting.cs:95-100` 的初始由 `StarterMoveIdx % 3` 决定。
- `ScrollsOfBitingNormal.cs:22-25` 第一只随机，后续轮转，第四只固定 `2`。
- `MonsterInitialVariants.cs:36-41` 标成「1/2/3号位初始」；第四只固定 `MORE_TEETH`，但会标成「3号位初始」。标签应表达「随机起始 A/B/C」而不是位置。

**Chomper 的初始标签不是号位**

- `Chomper.cs:63` 初始由 `ScreamFirst` 决定，不是槽位。
- `ChompersNormal.cs:18-25` 第二只 `ScreamFirst=true`；`TunnelerNormal.cs:26-32` 唯一 Chomper 也 `ScreamFirst=true` 且列首位。
- `MonsterInitialVariants.cs:21-25` 把 `SCREECH_MOVE` 标成「2号位初始」；Tunneler 中的 Chomper 是 1 号位，标签错误。

**Test Subject 的 `RESPAWN_MOVE` 没有入边**

- `TestSubject.cs:176-182` 通过 `SetMoveImmediate(DeadState, forceTransition: true)` 进入 `RESPAWN_MOVE`；状态机里没有静态入边。
- 面板的 dead-cell 隐藏会把 `RESPAWN_MOVE` 当成不可达；`REVIVE_BRANCH` 变成没有来源的悬空条件框。
- 这不是数值错误，但会让复活阶段的状态图断裂。

**Queen 的死亡分支覆写只在部分情况成立**

- 游戏 `Queen.cs:150-151` 的 `Box1` 死亡分支目标仍是 `OFF_WITH_YOUR_HEAD_MOVE`。
- `Queen.cs:249-251` 的 `SetMoveImmediate(EnragedState)` 只在当前 `NextMove == BurnBrightForMeState` 时触发，不会改写状态机分支。
- `MonsterIntentMetadata.cs:561-564` 把 `Box1` 的 `OFF` 目标直接改成 `ENRAGE`。如果玩家在第一次 `BurnBright` 之前击杀 TorchHeadAmalgam，实际会走 `OFF`，面板显示 `ENRAGE`；常见循环下则碰巧一致。这是部分错误，不是完全错误。

**次要项**

- `Exoskeleton` 状态机声明 4 个槽位分支，但 `ExoskeletonsWeak` 只有 3 个槽位；面板会多显示「4号位」变体。

- `MonsterIntentMetadata` 注释仍说会调用 `GetStateWeight`，实际 `BuildState` 使用裸 `sw.GetWeight()`；注释与实现不一致。

## 8. 古代遗物池

### 8.1 已核对正确的部分

`AncientPoolMap.cs` 的 8 个先古之民中，成员集合和大部分分组与 v0.113.1 源码对应：

- Pael 的三池与动态爪/牙/生长/军团选项。
- Vakuu 的三池。
- Tanx 的 9 个基础武器 + Tri-Boomerang。
- Nonupeipe 的 9 个基础遗物 + Beautiful Bracelet。
- Darv 的 11 个有效遗物组 + Dusty Tome 成员集合。
- Neow 的动态池补充逻辑。

静态表约 103 个遗物 ID。这个数量本身说明它是手工内容表，不是公式。

Tezcatara 和 Orobas 有池归属错误，见 8.2；Darv 的幕限制和结构问题见 8.3；Neow 的缺失项见 8.4。

### 8.2 Tezcatara 和 Orobas 池归属错误

Tezcatara：

- 游戏 `OptionPool2` 是 `BiiigHug / Storybook / ToastyMittens`（`Tezcatara.cs:73-89`）。
- `SealOfGold` 在 `OptionPool3`（`Tezcatara.cs:91-109`）。
- Mod 把 `SEAL_OF_GOLD` 放在池 2（`AncientPoolMap.cs:188`），池 3 没有它。

Orobas：

- 游戏 `OptionPool1` 是 `ElectricShrymp / GlassEye`（`Orobas.cs:33-47`）。
- `SandCastle` 在 `OptionPool2`（`Orobas.cs:49-67`）。
- Mod 把 `SAND_CASTLE` 放在池 1（`AncientPoolMap.cs:206`），池 2 没有它。
- 池 1 还有一个 `PrismaticGem` 与 `SeaGlassOptions` 的二选一占位（`Orobas.cs:69-84`）。Mod 把 `PRISMATIC_GEM`、`SEA_GLASS` 当成两个独立成员，池 1 显示 5 项；实际每次只在 2 个基础项 + 一个二选一占位中抽，池 1 分母不应按 5 个等概率成员算。
- `SEA_GLASS` 的历史标题带角色后缀，例如 `SEA_GLASS.SILENT.title`（`SeaGlass.cs:25-35`）。历史分析截取得 `SEA_GLASS.SILENT`，而池表写 `SEA_GLASS`，聚合命中不了；该遗物的选择率会长期显示 0，并从分母中漏掉。

这些错位在 v0.111.1 已存在，不是 0.113.1 新改动。

### 8.3 Darv 的幕限制和结构错误

`AncientPoolMap.cs:287-293`：

```text
ECTOPLASM = 2
SOZU = 2
PHILOSOPHERS_STONE = 3
VELVET_CHOKER = 3
```

游戏 `Darv.cs:194-200`：

```text
Ectoplasm: CurrentActIndex == 1  -> 第 2 幕
Sozu:      CurrentActIndex == 1  -> 第 2 幕
PhilosophersStone: CurrentActIndex >= 1 -> 第 2 幕或第 3 幕
VelvetChoker:      CurrentActIndex >= 1 -> 第 2 幕或第 3 幕
```

`CareerStatsSection.cs:1170-1171` 会用 `ActGate` 给遗物名追加「仅在 Act N」。因此：

- Ectoplasm、Sozu 标「仅 Act 2」正确。
- PhilosophersStone、VelvetChoker 标「仅 Act 3」错误；它们在第 2 幕也能出现。

结构上，游戏 `Darv.cs:150-169` 是：

1. 从 11 个 `ValidRelicSet` 中按筛选条件每组抽 1 个。
2. 打乱这组结果。
3. 50% 取前 2 个并追加 `DustyTome`，50% 取前 3 个。

Mod 把 12 个遗物压成一个等权池（`AncientPoolMap.cs:278-286`），因此：

- 每个遗物的出现概率被平均化，和游戏的「组内抽 1、再取 2/3」不等价。
- `DUSTY_TOME` 的 50% 追加概率被当成普通成员。
- 选取率分母和单个遗物的期望都不对。

Darv 只会在第 2 幕及以后出现（`RunManager.cs` 的 `Acts.Skip(1)`），`ActIndex=0` 的共享标签可以保留。

### 8.4 Neow 静态回退不完整

`AncientPoolMap.cs:130-166` 的 Neow 回退表有两类问题。

第一，缺少 v0.113.1 的部分遗物：

- Positive 池缺 `PHIAL_HOLSTER`、`WINGED_BOOTS`、`SCROLL_BOXES`、`NEOWS_TALISMAN`。
- Curse 池缺 `DOWSING_ROD`、`HEFTY_TABLET`、`NEOWS_BONES`、`NEOWS_SACRIFICE`、`SILKEN_TRESS`。

第二，`SCROLL_BOXES` 和 `SILKEN_TRESS` 放反了。游戏 `Neow.cs:68-109` 中：

- `ScrollBoxes` 在 Positive 池。
- `SilkenTress` 在 Curse 池。

Mod 静态表把 `SILKEN_TRESS` 放 Positive，把 `SCROLL_BOXES` 放 Curse。`HydrateNeowPools` 会把 `SILKEN_TRESS` 移到 Curse，但没有把 `SCROLL_BOXES` 移回 Positive；它只做添加，不删除错放的 Curse 项。因此即使动态读取成功，`SCROLL_BOXES` 仍会留在 Curse 池，按错误分母计算选取率。

动态读取失败时，上述缺失项也会直接消失。这是中低风险内容表问题，但会直接影响 Neow 的先古遗物统计。

`HydrateNeowPools` 还有三个结构性问题：

- `Lazy` 只执行一次。任一步骤抛异常后永久使用手写表，进程内不会重试；`neow == null` 时也没有告警。
- 它只添加、不删除或移动错放项。`SCROLL_BOXES` 已经在 Curse 池时，正面池的添加条件 `!pool1.Contains` 会阻止它进入正面池。
- 它按属性名猜池（`Curse`/`Bundle`/`Empower`）。0.113.1 的 `Neow` 已经不用 `Bundle`/`Empower`，这个启发式对 `ScrollBoxes` 失效；`AllPossibleOptions` 的兜底又会把未知项统统塞进正面池，部分反射失败时可能把诅咒项归错。

### 8.5 非公式内容表

以下内容表不是游戏公式，但同属「与游戏实际情况相关」的硬编码，后续改版需要维护：

- `Util/NameLookup.cs`：427 个英文回退名称。
- `NameLookup.Ancient` 只查 `events` / `encounters`，不查 `ancients`。因此 4 个中文长老名与官方不一致：PAEL/佩尔、TEZCATARA/特兹卡塔拉、OROBAS/欧洛巴斯、NONUPEIPE/诺奴佩普。`DeathCause` 也不查 `ancients`，长老死亡行可能显示原始 ID。
- `CareerStatsSection.cs`：角色顺序、先古 ID、已移除 Boss ID。
- `CareerStatsSection.BossActInfoForActIndex` 假设幕顺序是 Overgrowth/Hive/Glory/Underdocks；v0.113.1 实际是 Overgrowth/Underdocks/Hive/Glory。Boss 幕号会错位。
- `BetaRemovedBosses` 的 `DOORMAKER_BOSS` 在当前两个版本都没有对应 encounter，过滤结构上是空操作。
- `ContributionMap`：没有硬编码具体卡牌/遗物 ID，主要是通用归因容器，不是内容表。

## 10. 贡献归因中的游戏数值

这部分不是概率/价格公式，但会直接影响贡献图显示。`CombatHistoryPatch` 和 `CombatTracker` 中有若干游戏倍率硬编码。

已抽查、当前版本基本一致但属于硬编码的项目：

| 项目 | Mod 值 | 游戏 | 风险 |
|---|---|---|---|
| 虚弱倍率 | `0.75` | `WeakPower.DamageDecrease = 0.75` | 中 |
| Paper Krane | `-0.15` | `PaperKrane.ModifyWeakMultiplier` | 中 |
| Debilitate 虚弱 | `1-(1-m)*2` | `DebilitatePower.ModifyWeakMultiplier` | 中 |
| 易伤 | `+0.5`、Paper Phrog `+0.25`、Cruelty | `VulnerablePower` / `PaperPhrog` / `CrueltyPower` | 中 |
| Colossus | 假定 0.5 倍 | `ColossusPower` 使用 DynamicVar | 中 |
| 君王之剑基础伤害 | `const 10` | `SovereignBlade._baseDamage = 10` | 高（数值一变就错） |

这些项目在 v0.113.1 当前数值下多数能对上，但它们是「复制数值」而不是读取游戏变量。后续平衡补丁会直接造成显示偏差。`CombatHistoryPatch` 的 107 个补丁没有全部逐条证明数学等价；本报告只标记已知硬编码点。

## 11. 不是游戏公式的部分

以下内容不应按「游戏公式错误」处理：

- `CombatTracker` / `CombatHistoryPatch` 的归因规则是自定义统计模型，不是游戏原始公式。
- `RunHistoryAnalyzer` 的胜率、选取率、死亡原因、平均卡组等是本地统计口径。
- `CareerStatsSection` 的颜色阈值、排序、显示格式是产品选择。
- `NameLookup` 是名称回退表，不是公式；缺失时回退到游戏本地化或内部 ID。
- UI 布局、颜色、字体、动画不属于本轮范围。
